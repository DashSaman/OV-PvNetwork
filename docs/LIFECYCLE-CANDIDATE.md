# PVN-1026 / 1.0.42 lifecycle candidate

This is an unmerged candidate. Public stable remains 1.0.37. Production remains the previously authorized 1.0.40 checkpoint; this candidate has not been deployed there.

`pvnetwork update v1.0.42 --yes` downloads the exact official release asset and its matching single-file SHA256. Before publication this command must fail rather than install a branch. An offline operator may pass `--archive /root/verified.tar.gz --sha256 <verified-hash>` with an immutable version. Same-version replacement and downgrade are refused. Existing rooted checkouts require explicit `--adopt-rooted`; adoption preserves the previous application, environment and data. Builds use private pinned tools and frozen project locks, without changing host package installations.

The update sequence is verified native backup, isolated build, matching schema head, clone canary with lifespan disabled, owned proxy maintenance, writer pause, final quiesced backup, atomic application pointer switch, health verification and finalization. Only the panel and its explicitly versioned jobs pause. OpenVPN, node agents, tunnels, firewall and unrelated services are excluded. Old assets and previous releases are retained. A failed pre-switch build does not restart the panel. Durable root-only journals support `pvnetwork recover --yes` after process interruption.

`pvnetwork backup --json` creates a native PostgreSQL dump or SQLite online snapshot and actually restores it into a disposable database/file. Every table has column/count/row digests. Checksums cover source, environment, runtime files and database. SSH trust files, panel data and owned AnyConnect/push encryption keys are included, excluding volatile jobs and SQLite sidecars. Runtime files must remain unchanged throughout the database snapshot. Backup directories are root-only; transaction backups remain pinned against retention. PostgreSQL client major version must be at least the server major, and a remote role needs permission to create/drop uniquely owned rehearsal databases.

`pvnetwork restore BACKUP_ID --yes` verifies the selected archive/schema, pauses writers, takes a final recovery backup, restores database and runtime keys/files, verifies health and resumes jobs. Host bindings, administrator/JWT credentials and integration secrets remain current; supported nonsecret panel settings are restored. PostgreSQL restores into a new database and switches the protected connection setting, retaining the previous database. SQLite uses validated atomic replacement. Interrupted restore recovery returns to the final pre-operation rows, keys and configuration. Existing v1 PostgreSQL uploads use this engine after checksum and actual clone-restore verification; they cannot recover keys that were absent from their old format.

`pvnetwork rollback --yes` switches to the retained compatible application while preserving current live data. A schema-changing update is deliberately refused until a separately validated migration/restore path exists. This candidate does not claim migration of arbitrary old schemas, final interactive CLI, public ACME, native node deployment or Internet client traffic.

Local evidence: real systemd Ubuntu 24.04 update/restore/rollback, actual SIGKILL update recovery without changing panel PID, actual SIGKILL restore recovery, post-switch restore failure recovery, row/quota/UUID/device and environment preservation, encryption/SSH file restore, and an unrelated service PID preserved. PostgreSQL 16 native dump and actual restore of the complete 27-table current schema matched every row digest. A dedicated CI PostgreSQL service tests empty-schema creation/head and atomic failure rollback; its isolated trust authentication is not a Production authentication test. Exact commit CI and remaining integration gates must be recorded before release.
