# PVN-1029 — English/Persian operational CLI implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement task by task. The user's one-assistant limit has already been used in this mission; work directly without further delegation.

**Goal:** `pvnetwork` opens the requested 25-item bilingual interactive menu, with useful automation subcommands, explicit mutation scopes and the existing native lifecycle safety rules.

**Architecture:** A small CLI entry point owns parsing, translated menus, confirmation and exit codes. Focused local operations implement bounded read-only diagnostics and a fixed-loopback authenticated API client; existing lifecycle/configuration workers remain the mutation engines. Installed source comes from the checked release and the existing panel Python environment.

**Tech stack:** Python 3.12 / stdlib, current pinned Python dependencies, existing Bash launcher, systemd, native SQLite/PostgreSQL and existing loopback API. No new dependencies, provider, arbitrary shell execution or network installer.

**Spec:** User's final completion mission, section 7 (25 menus, EN/FA, automation, help, standard error codes, sanitized logs, dry run, confirmation; doctor read-only / repair scoped), plus preservation/Production rules in `AGENTS.md`. The user requests autonomous completion; routine implementation choices do not require new approval. This plan does not authorize a live deployment or service/node/firewall/SSH change.

## Global constraints

- Candidate 1.0.45 / PVN-1029 is stacked on candidate 1.0.44 / PR #59; public stable and Production remain unchanged until their separate gates.
- No arguments/stdout/logs/browser files containing credentials, private keys, raw DB URLs or bearer tokens. Secret input uses hidden prompts or bounded stdin JSON. Support exports use a structured allowlist, not raw logs/configs/customer data.
- Read-only commands do not invoke mutating lifecycle helpers, write error/config files or run repair implicitly. Collect exit statuses explicitly; never use `lifecycle.run` for diagnostics because its failure path writes private state.
- Mutations require a concrete allowlisted action and confirmation (`--yes` for automation); `--dry-run` returns the exact plan before changing anything. No OpenVPN restart, global firewall/routing change, broad permission repair or arbitrary command option.
- Node actions target a registered ID through existing API/native engines; SSH credentials stay in memory and errors remain sanitized. The main-admin root-local API token is short-lived, sent only to a fixed loopback endpoint with redirects/proxies disabled, and never printed.
- Reuse the native backup/update/restore/rollback/recovery commands and journals. Preserve all existing noninteractive lifecycle options, immutable versions and interrupted recovery.

## Review focus

1. A failed diagnostic must not turn into repair or write an error file into the runtime.
2. JSON, errors, subprocess diagnostics and support archives must not export secrets or customer/Production identifiers.
3. Dry-run, EOF, Ctrl-C, invalid menu input and missing confirmation must fail before mutation.
4. Existing automation must still use the verified lifecycle engine and preserve recovery after process/service failure.
5. Loopback API authentication must not leak through proxies, redirects, argv, support files or long-lived credentials.
