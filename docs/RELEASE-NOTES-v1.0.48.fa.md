# نامزد v1.0.48 — PVN-1032

ثبت بستهٔ دامنهٔ DNS روی SQLite با خطای `no such column:
uq_domain_activity_user_node_domain` شکست می‌خورد. مسیر نوشتن از syntax و توابع
مخصوص PostgreSQL استفاده می‌کرد. شناسهٔ BIGINT جدول موجود نیز در SQLite به‌صورت
خودکار مانند INTEGER rowid ساخته نمی‌شود.

اکنون درج و توابع کمینه/بیشینه متناسب با دیتابیس انتخاب می‌شوند و کلید یکتای
کاربر/نود/دامنه حفظ می‌شود. شناسه‌های SQLite داخل همان دستور اتمیک INSERT و
زیر قفل نویسنده ساخته می‌شوند؛ جدول و داده‌های موجود بازسازی نمی‌شوند.
PostgreSQL همچنان شناسه را در دیتابیس تولید می‌کند. کنترل UUID، نود و تخصیص،
محدودسازی دامنه به سطح سایت، زمان‌ها و افزایش شمارنده حفظ شده‌اند.

خطای اولیه پیش از اصلاح بازتولید شد. پنج آزمون SQLite واقعی پاس شدند، شامل
دو اتصال نویسندهٔ هم‌زمان در حالت DELETE و WAL، بستهٔ ۱۰۰۰ دامنه و بازگشت کامل
تراکنش با خطای SQL تزریق‌شده. مجموعهٔ کامل Linux شامل ۷۰۹ آزمون بود: ۷۰۳ موفق
و شش مورد مخصوص PostgreSQL ردشده از اجرا. هر شش مورد سپس روی PostgreSQL واقعی
و موقت پاس شدند، از جمله همان بررسی تجمیع دامنه و gateهای نصب و امنیت موجود.

به migration یا بازسازی جدول نیاز نیست. برای ارتقا از چرخهٔ عمر بومی تأییدشده
با بکاپ تازه استفاده شود. rollback کد schema را تغییر نمی‌دهد، ولی خطای قبلی
ثبت دامنه در SQLite را برمی‌گرداند؛ دیتابیس حفظ شود. این نامزد Production را
تغییر نداده است. CI نهایی همان commit، اعتبارسنجی باقی مأموریت، فایل‌های عمومی
تغییرناپذیر و مجوز محدود استقرار هنوز gateهای باز هستند.

مراجع پیاده‌سازی: [جداسازی نویسنده در SQLite](https://www.sqlite.org/isolation.html)
و [upsert در SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#sqlite-on-conflict-insert).
